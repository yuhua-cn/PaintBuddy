# 绘画伴侣（Painting Buddy）· Windows 版

一个 C++ 实现的绘画行为无感记录 + 统计分析工具。界面与图表仿 iOS 设计语言（Win32 + Direct2D 全自绘，零第三方 UI 依赖）。

---

## 一、它做什么

### 1. 无感记录（前台为绘画软件时才记录）
仅当前台软件是 **Photoshop / Clip Studio Paint（含优动漫 PAINT）/ SAI2**（可在设置页增删）时记录：

| 类别 | 内容 |
|---|---|
| 键盘 | Ctrl+Z = **撤回**（特殊操作）；Ctrl+Y、Ctrl+Shift+Z = **重做**；其余按键与修饰键组合 = 普通操作。**连续相同键 0.8 秒内合并计数**（窗口可在设置页改） |
| 鼠标 | 移动轨迹（时间戳 / 坐标 / 速度）；左键按下→抬起 = 一次笔画起止 |
| 数位笔 | Raw Input + HID 解析，与鼠标**并行**工作。动态枚举所有 Digitizer（Usage Page 0x0D）设备，覆盖 **External Pen 0x01 / Integrated Pen 0x02 / Touch Screen 0x04** 及任何数位板/数位屏（无需品牌白名单）。采集时间戳 / 坐标 / 速度 / 压力 |
| 归属规则 | **落笔/按下瞬间若有任意键按住，整次鼠标或数位笔操作都记为键盘操作**（普通操作，`src=0`，不再计为画笔；带原始时间戳存为原始数据）。按键状态用 `GetAsyncKeyState` 实时查询，不依赖会残留的钩子缓存 |
| 前台事件 | 切换窗口、窗口标题变化均记为原始事件（用于判定"切出但仍在操作"） |

操作分类：普通操作 / 撤回（特殊）/ 重做（特殊）/ 画笔。

### 2. 分类阈值：统计你的习惯自动得出
- **n1**：普通间隔上限。小于 n1 = 正常操作间隔。
- **n2**：打断下限。`n1 ≤ 间隔 < n2` = **暂停绘画**（计入序列，不算打断）；`≥ n2` = **打断绘画**。
- 推导方法：对全部相邻操作间隔做**对数空间最大跳变检测**（多峰分布的峰谷即天然分类点）；无跳变时退化为百分位。
- **深度 / 浅度绘画**：一个作画块内**典型间隔（中位数）**越小越密集 → 深度；分界同样由全部作画块的中位间隔自动统计。
- 三者均可在设置页固定（填 0 = 自动）。推导方法与当前值显示在设置页与总览页。

### 3. 可视化一：总览（睡眠式甘特图）
- **列 = 时间**，采用**可变单位**：每个连续段的列宽按 `sqrt(时长)` 压缩（短段可见、长段不吞屏）。
- **行 = 三个状态行**：深度绘画 | 浅度绘画 | 暂停绘画。
- 每个连续作画段在深/浅行内占一条横向带；暂停段在暂停行。带内按 **撤回（红）/ 画笔（橙）/ 普通（蓝）** 的时间占比画横向色段；列宽不足 ~24px 时与行底色按比例混合，**自然"糊"成一片**（需求规格）；放大则还原为离散小段。
- **打断绘画 = 贯穿三行的一整块竖向通栏带**，标注真实时长；**显示封顶 1 小时**（超出标注"显示封顶 1 小时"）。
- 头部刻度：日期主刻度 + 日内时刻副刻度（按段长自动选 1/2/3/6 小时步长），标签带碰撞检测不重叠；竖参考线淡色置于数据层之上。
- 交互：甘特区**滚轮 = 以鼠标为中心缩放**（上滚放大、下滚缩小）；拖拽平移；标题栏"适应/放大/缩小"；悬停显示明细。**放大到一定程度（每笔操作平均 ≥6px）后，概括色块交叉淡入为逐笔操作明细**（每一笔、每一次撤回在时间轴上的独立色块，够宽时标注操作名），缩回时反向淡出；动画约 0.28s 且带滞回，避免在临界缩放处闪烁。

### 4. 可视化二：操作习惯与内在关联
序列由 **普通操作 / 撤回·重做 / 画笔 / 普通间隔 / 暂停绘画** 五态构成（**打断不进入序列**——跨会话无行为因果关系，计入会稀释真实规律）。

- **连续事件合并**：除**画笔**与**撤回/重做**外，相邻间隔 < 1 秒的操作合并为一个事件，时间戳取组内最早者（`Op::merged` 记录被合并的原始操作数）。画笔与修正类操作独立成组、不被吸收，因此它们的计数与时刻始终精确。合并只影响统计口径，**落盘的原始事件流不变**，改规则无需重录历史。

- **一阶转移**：5×5 条件概率热力图 P(下一状态 | 当前状态) + 状态占比条。
- **长程关联**：滞后 2–5 阶的条件概率热力图 + **提升度**热力图（条件概率 ÷ 边缘概率，消除高频状态的必然延续）+ 自动检出"显著长程关联"清单（提升度 ≥1.5 且样本 ≥20）。
- **二阶条件转移**：固定第二个状态，行 = 第一个状态、列 = 第三个状态，捕捉"连续两件事之后才出现什么"。
- **习惯概览**：作画时长 / 有效占比 / 撤回 / 画笔 / 深浅块 / 打断统计，阈值推导说明，Top5 高频转移。
- 支持"全部历史"与"指定日期"两种口径；分析在后台线程执行，界面不冻结。

### 5. 录屏：一个绘画文件 = 一个缓存文件夹 = 一张卡片
- **触发**：前台是目标软件 **且** 正在操作（有笔画进行中，或最近有输入采样/完成操作）。
- **停止**：只有 **切换到另一个绘画文档 / 关闭录制 / 退出程序** 才收尾保存。**停顿、空闲、切到别的软件再切回来，都续写同一个文件**，不另开新文件。
- **归档**：每个绘画文档对应 `videos\<文档名>\` 一个缓存文件夹，该文档的多次录制会话都落在其中；缩略图存为文件夹内 `thumb.png`。旧版散落在 `videos\` 根目录的文件不移动，界面按文档名聚合为一张"未归档"卡片。
- **视频里不含停顿与无操作时间**：无输入活动期间的帧直接丢弃不写；已写入帧按序号连续排时间戳，播放时看不到任何等待。
- **连续长运笔（数秒）不会被切断**：活跃判定用「采样级时刻 + 笔画进行中」标志，而不是「已完成操作」的时刻——运笔途中不产生完成的操作，若只看后者就会把长笔画中途判为空闲切断。
- 捕获目标 = **绘画软件那个窗口**（Windows.Graphics.Capture，关闭黄色边框），不是整块屏幕。
- H.264/MP4（Media Foundation Sink Writer），**文件名 = 绘画文档名 + 会话起始时间戳**（如 `shijian\shijian_20261017_231142.mp4`）。
- 短于 `minClip` 的文件自动丢弃（仅删本程序刚生成的临时输出）。
- 系统不支持 WGC 时自动降级：键鼠与笔的记录不受影响，录屏页显示原因。

**录屏页 = 卡片列表**（无任何说明性卡片）：
- 一张卡片 = 一个绘画文档（如 `shijian`、`插画2`），左侧为该文档录制的**缩略图**（取首帧等比缩放，后台生成），中部显示段数/总时长/总大小。
- 右侧两个按钮：**导出** = 把该文档的全部录制按时间顺序**拼接为一个视频**（解码后重编码，兼容各段分辨率不同；在后台线程执行并显示进度，导出中点该按钮可取消；默认保存到系统「视频」库）；**清空** = 把该卡片整体移入回收站（需二次确认，可还原）。
- 点击卡片本体 = 打开该文档的归档文件夹。

> 已移除的参数：`clipGap`（超过多久不写帧）与 `idleStop`（空闲多久结束片段）。会话不再因空闲切片，「无活动多久后停止写帧」改为内部固定窗口（`Recorder.cpp` 的 `kActiveWindowUs`，1.2s），不再是用户可配项。

## 二、数据与隐私

- 全部数据仅存本机：`%LOCALAPPDATA%\PaintingBuddy\`
  - `logs\YYYYMMDD.jsonl` —— 事件流，只追加不改写历史（含轨迹/压力/时间戳原始数据）
  - `videos\<文档名>\*.mp4` —— 录屏片段（一个绘画文档一个文件夹）
  - `videos\<文档名>\thumb.png` —— 该文档卡片的缩略图
  - `videos\.thumbs\*.png` —— 未归档散文件卡片的缩略图（不移动用户既有文件）
  - `config.json` —— 设置
  - `pb.log` —— 诊断日志
- 不上传、不联网。关闭窗口 = 最小化到托盘继续记录；托盘右键可暂停/恢复/退出。

## 三、构建与运行

依赖：Visual Studio 2022 Build Tools（VC 工具集 + Windows 10/11 SDK，含 C++/WinRT 头）。

```
build.bat            # 增量构建 → build\PaintingBuddy.exe
build.bat rebuild    # 全量重建
build_test.bat       # 编译并运行分析层单元测试（27 项断言）
build_preview.bat    # 生成合成样本 + 离屏渲染图表预览 PNG
```

直接双击 `build\PaintingBuddy.exe` 运行（无需管理员权限；单实例保护）。

### 第二轮修复（按用户反馈）
- **数位笔无数据**：HID 报文解析改为多形态探测——直读 / 前缀已收集的 Report ID / 穷举 1–255，首次成功后缓存形态；并新增解析失败诊断（连续 32 次失败记录报文原文）。总览页"数位笔"磁贴现在显示"已解析 N 点（报文 M）/ 等待笔报文（报文 M）"，便于直接判断笔管线是否工作。
- **默认深色**：新建配置默认深色；旧配置（ver<2）启动时自动迁移为深色。设置页可切回浅色。
- **无法退出**：关闭窗口弹出「是=退出程序 / 否=最小化到托盘继续记录」；设置页底部新增红色"退出程序"按钮；托盘右键"退出"改为真正销毁窗口。
- **设置页错位**：卡片高度改为按行数精确计算（46 + n×rowH），开关/输入框/提示同行对齐；截图逐页验证通过。
- **总览标题**：改为"总览图"。

### 第三轮修复（按用户实测日志定位）
用户实测日志给出决定性证据，修正了前一轮的错误判断（"窗口类型导致笔失效"被隔离实验证伪：message-only / 显示的 popup / 从未显示的 popup 三种窗口都能收到 WM_INPUT）。

- **数位笔真正根因 = Windows Ink 接管**：日志显示 4 个数位设备均注册成功（含 Wacom 笔 VID_056A usage=0D:02），但运笔时从无 `first WM_INPUT arrived`，且出现 `VID_0000&PID_0000 usage=0D:02`（Windows Ink 虚拟笔设备）。结论：数位笔开启 Windows Ink（Wacom 默认开）后，笔数据被系统墨迹管线接管，不再向后台 Raw Input 监听窗口投递原始 HID 报文，而是转成"注入的鼠标事件"（dwExtraInfo 带 FROMTOUCH 签名）；旧代码恰恰把这些注入事件当噪声丢弃，导致笔一条都没记到。
  - **修复（回退采集）**：当原始 HID 笔通道静默（从未收到真实笔采样）时，把注入的鼠标事件回收为画笔笔画——按下=落笔、移动=运笔、抬起=收笔，复用原笔笔画落盘（轨迹/时间戳/速度完整，压力按 1.0 记）。原始 HID 路径保留（关闭 Windows Ink 时带真实压力），两条路互斥，不会重复计数。首次触发回退会记日志 `RAW HID silent -> injected-mouse fallback ACTIVE`。
  - 想要带压力的完整笔数据，可在 Wacom 驱动里关闭"使用 Windows Ink"，程序会自动切回原始 HID 通道（日志出现 `first sample parsed OK`）。
- **录屏两个确凿 bug（日志证实）**：
  - `size changed 1726x944 -> 1727x944` 无限循环：编码尺寸按 H264 要求对齐成偶数（1727→1726），却拿它跟帧的真实尺寸（1727）比对，导致每帧都误判"尺寸变了"→无限重启录制，一个片段都录不成。改为用"捕获真实尺寸"比对并容忍 ±2px 抖动。
  - `Finalize 失败 0xC00D4A44`：0 帧片段不应调用 Finalize。改为零帧时跳过 Finalize、直接删除空文件。

### 第四轮修复（按用户实测日志定位）
- **录屏 `WriteSample 失败 0x80070057`（E_INVALIDARG）**：尺寸抖动修好后仍每帧失败。根因是**帧池按窗口真实尺寸（1727，奇数）创建，而编码媒体类型按 H264 要求声明为偶数尺寸（1726）**，surface 尺寸与媒体类型不符 → SinkWriter 拒收每一帧 → 0 帧 → 无限重启刷屏。修复：帧池也用偶数对齐尺寸创建，三者一致。另加**连续空片段熔断**：连续 3 个 0 帧片段即停止自动录制，杜绝任何写帧失败导致的无限重启刷屏。
- **数位笔压感（Windows Ink 通道）**：Ink 开启时笔走 `WM_POINTER`，压感在 `POINTER_PEN_INFO.pressure`（0..1024）。后台进程**不能**用 `RegisterPointerInputTarget` 抢占（会导致前台绘画软件收不到笔）。正确做法：从 Ink 促进的鼠标事件 `dwExtraInfo` 低字节还原 pointerId，用 `GetPointerPenInfo` 查系统全局笔状态取压感——非侵入、不抢焦点。注入回退采集的每个点现在都带真实压感；查不到时退回 1.0（不影响轨迹/分类）。首次取到压感记 `POINTER pressure ACTIVE`，取不到记 `POINTER pressure unavailable`。

> 待真机验证（沙箱无物理数位笔）：Ink 开启下用笔画几笔，pb.log 应出现 `POINTER pressure ACTIVE`，且落盘的 `'p'` 记录带非零 maxp/avgp；录屏应不再刷 `WriteSample 失败`、能生成正常 MP4。若压感日志为 `unavailable`，说明该驱动的 pointerId 还原方式不同，把日志发我进一步适配。

### 第五轮修复（按用户实测反馈定位，推翻此前 Ink 假设）
用户反馈：CSP 里数位笔**能正常解析**，证明原始 HID 通道本身是通的 —— 第四轮"Windows Ink 接管"的解释不成立。代码审查确认三个真实缺陷：

- **漏注册 HID Usage `0x01`**：此前只注册 `0x02 / 0x04 / 0x0C`，枚举过滤器也跳过 `0x01`。而本机 Wacom 存在一个 `0D:01` 集合（`pen_diag` 实测枚举到）。补注册后启动日志由 `4 device(s) parsed` 变为 **`registered 4 digitizer usages (01/02/04/0C); 5 device(s) parsed`**，多出的正是该集合 —— 证实它此前根本没被监听。
  - 术语澄清：HID 规范里 `0x01` 官方名是 *Finger*，"External Pen" 是 `POINTER_DEVICE_TYPE_EXTERNAL_PEN=2`（另一套枚举）。但设备确实存在且必须监听。
- **`OnKeyDown` 缺前台过滤** → 对应"绘画软件非前台也记键盘为操作数"。鼠标/笔路径都有 `if (!TargetActive()) return;`，唯独键盘漏了。已补上。
- **`AnyKeyDown()` 依赖会残留的 `keysDown` 缓存** → 对应"CSP 记成操作数而不是笔画"。它靠钩子 KEYUP 清除缓存，而 KEYUP 在切前台 / UAC / 安全桌面 / 全屏应用时会丢失；一旦残留就**永久返回 true**，导致每次落笔都判为"有键按下"→ 按需求规则整笔记为键盘操作，画笔统计恒为 0。已改为 `GetAsyncKeyState` 实时遍历物理键态。

配套改进：
- **笔笔画看门狗**（400ms 静默自动收尾）→ 对应"只有用数位笔切换前台时才有一笔记录"。PS 可能吞掉抬笔报文，笔画挂着不收尾，直到切前台才被 `FlushPen` 挤出。
- **解析成功也打印原始报文 hex（前 20 条）**：此前只打失败，无法发现"解析成功但字段错位导致压感恒为 0"。
- `pen_diag` 同步注册全部 4 个 Usage，并在报告中按 Usage 细分统计（`usage 0x01/0x02/0x04/0x0C`），可直接看出数据来自哪个集合。

### 第六轮：录屏逻辑重构（按用户要求，不再打补丁）
`WriteSample 失败 0x80070057`(E_INVALIDARG) 的真正原因此前找错了方向——两轮都只在"尺寸对齐"上打转。重构后确认：**非压缩 RGB32 输入必须提供 `MF_MT_SAMPLE_SIZE` / `MF_MT_DEFAULT_STRIDE` / `MF_MT_FIXED_SIZE_SAMPLES`，缺失就会导致每帧被拒收**。

重构要点：
- **写入器惰性创建**：不再在开录时猜尺寸建 SinkWriter，而是等第一个「确实要写入」的帧到达后，从 `ID3D11Texture2D::GetDesc()` 取真实宽高再建。尺寸猜错这一整类 bug 从此不可能发生。
- **补齐非压缩输入必需属性**（上述三项 + `MF_MT_ALL_SAMPLES_INDEPENDENT`），并显式设定缓冲长度，避免长度为 0 被判为非法样本。
- **文件名取「文档名」而非整条窗口标题**（有单元测试覆盖，19/19 通过）：
  `shijian.psd @ 11.1% (图层 199, RGB/8)` → `shijian_时间戳.mp4`；
  `作品_线稿.csp - Clip Studio Paint` → `作品_线稿_时间戳.mp4`。
  处理顺序为「切分隔符 → 剥尾部 `*`/`+` → 去扩展名 → 再剥尾部」，顺序错了会残留 `.psd`（该缺陷正是被测试用例抓出来的）。
- **低资源占用**（按用户要求）：帧池仅 2 个缓冲；写入器惰性创建，空闲期不建编码器、切窗口不产生编码器 churn；空闲帧直接丢弃不进编码器（零编码开销）；保留 SinkWriter 默认节流以便编码器积压时自然回压，避免帧堆积吃内存；轮询 120ms；D3D 设备进程内只建一次。
- **双锁分离**：`cs` 只保护统计（界面读取永不阻塞），`writerCs` 保护写入器与捕获会话生命周期，避免 `WriteSample` 阻塞导致界面卡顿。
- `WriteSample` 失败日志限流（最多 3 条），配合既有的连续空片段熔断，不会再刷屏。

测试：`build_test_filename.bat` → **19/19 通过**（含用户日志里的三条真实标题）。

### 第七轮修复（按用户四点反馈，含日志与实验实证）
用户反馈四个问题，逐一从源码定位根因，并用 `pb.log` 与独立实验取证。

- **① 键盘按下时的鼠标/数位笔操作未记为键盘操作**（真因两处）：
  - `SerializeRecord` 的 `'m'/'M'`（鼠标）分支**漏写 `kb` 字段** —— 采集层 `AnyKeyDown()` 算出的归属标记根本没落盘，重载即丢失。
  - `RecordsToOps` 的 `'M'` 分支**硬编码 `src=1` 且忽略 `r.kbAttr`** —— 即使标记在，分析层也不认。
  - 修复：鼠标笔画与移动段落盘都写 `kb`；分析层按 `kbAttr` 归类（有键→`src=0` 键盘操作、不计画笔）。新增全链路回归测试（序列化→反序列化→转 Op）覆盖鼠标笔画/移动/数位笔三种记录，锁定不退化。
- **② 每一笔一个视频文件 → 改为一个绘画文件一个视频**：录屏会话此前按「空闲/切窗」不断收尾并新建文件（日志实证同一 `shijian` 文档 3 秒内产出两个 mp4）。改为**会话绑定绘画文档**：文件名 = 文档名 + 会话起始时间戳，停顿/切走再切回都续写同一文件，只有**换文档 / 关录制 / 退出**才收尾。
- **③ 连续长运笔（两三秒）被切断**：活跃判定只看 `lastOpUs`（**只在笔画收尾时更新**），运笔途中不刷新，走到一半就被判空闲——日志实证 `clip saved, 36 frames, 1.20s` 正好被切在 `idleStopMs=1200`。改为采集层维护**采样级活跃时刻 `actUs` + 笔画进行中 `strokeActive`**（无锁原子），录屏据此判活跃，长笔画不再被切断。同时**移除 `clipGapMs` / `idleStopMs` 两个参数**（设置页、config、夹取、界面文案全部清理），"无活动多久停写帧"改为内部固定窗口 `kActiveWindowUs`。
- **④ 连续约 100 个操作后两个图表都不更新**（真因两处）：
  - **无任何自动刷新**：`RequestAnalysis` 只在启动/改设置/点「重新统计」时调用，`SetOpListener` 从未注册。加轮询：以「最近操作时刻」水位线为信号，检测到新操作且超过 2s 节流就触发后台重算（`GanttView::UpdateData` 保留当前缩放视图，不弹回全图）。
  - **当天日志根本读不到**：事件写入器用 `fopen(...,"ab")` 持有句柄，`ReadWholeFile` 用 `CreateFileW(...FILE_SHARE_READ)` 打开同一文件 → 共享冲突 `err=32`。独立实验（`tests/share_probe.cpp`）证实：`fopen("ab")` 下读取端**任何**共享模式都失败；改用 `_fsopen(...,_SH_DENYNO)` + 读取端 `FILE_SHARE_READ|WRITE` 后可边写边读。日志实证 `[analysis] 完成，用时 0 ms`（拿到空数据）。这是「图表恒空」的主因，已修复。分析加载另跳过轨迹点解析（当天日志数 MB 多为轨迹），使边画边重算低开销。

> 本轮验证：`build_test.bat` **34/34 通过**（新增 7 项键盘归属回归）；主程序全部 `.obj` 编译通过、链接验证 `LINK_OK`（`build.bat` 最后一步 `LNK1104` 仅因程序正在运行、exe 被占用，非代码问题，关闭程序后重编即可生成新 exe）。

### 第十轮：流式安全缓存（分片 MP4）+ 导出失败修复
用户报告「导出失败：无法确定视频分辨率」，并要求「可随意中断、随时可打开的流式视频缓存」。

- **导出失败根因 = 属性类型用错（我自己引入的）**：`MF_MT_FRAME_SIZE` 在 SDK 中是 **UINT64**（高 32 位=宽、低 32 位=高），录制端用 `SetUINT64` 写入，而 `ProbeVideo` / `MakeThumbnailFromVideo` 却用 **`GetUINT32`** 读取 → 类型不匹配必然失败 → 分辨率恒为 0 → 报「无法确定视频分辨率」。改为 `GetUINT64` 后实测用户真实的 74MB 录屏可正确读出 `1726x990 / 37.17s`。
- **「关闭软件后才读得出来」根因 = 普通 MP4 的索引写在文件尾**：`moov` 要到 `Finalize()` 才落盘，录制中进程被强杀/断电就得到无索引的坏文件（用户目录里那个 79 字节文件即此类）。
  - **改为分片 MP4（fragmented MP4）**：`MFCreateFMPEG4MediaSink` + `MF_MPEG4SINK_MOOV_BEFORE_MDAT`（索引写在文件头）+ `MF_MPEG4SINK_MIN_FRAGMENT_DURATION`（1 秒分片），并配 `MF_MT_MAX_KEYFRAME_SPACING=1000` 让关键帧与分片对齐（解码必须从关键帧起，只缩分片不管关键帧实测仍丢约 0.8 秒）。
  - 效果：**录制过程中文件即可打开播放；随时中断都保留已写内容**，代价上界约 1 秒。创建失败时自动回退普通 MP4，不比改造前差。
- **健壮性修复**（都由本轮测试暴露）：
  - `MFCreateFile` 必须用 `MF_OPENMODE_DELETE_IF_EXIST`：`RESET_IF_EXIST` **不会创建文件**，文件不存在时返回 `0x80070002`——这会让分片路径每次失败并静默回退（对照实验 `tests/mfpath_probe.cpp` 实测确认，结论已固化进代码注释）。
  - 分片路径**不能再调 `AddStream`**：sink 创建时已建好视频流，重复添加会产生一条无样本空流，`Finalize` 报 `MF_E_SINK_HEADERS_NOT_FOUND (0xC00D4A45)`。
  - `ConcatExport` 目标尺寸改为取**第一个能解析出分辨率的文件**，残缺文件不再拖垮整个导出；缩略图同样逐个尝试。
  - 丢弃过短文件时增加删除重试：句柄刚释放时 `DeleteFileW` 会失败，不重试就残留无索引的空壳文件。

新增可复现验证：
- `build_fragtest.bat` → **17/17 通过**（`tests/fragtest.cpp`）：用「写完全部帧但不 Finalize 直接释放」模拟进程被强杀，验证未收尾文件仍可打开、分辨率正确、能解码出画面、能生成缩略图；并验证**导出拼接**在「正常文件 + 未收尾文件」混合卡片上成功，产物帧数 = 两段之和（无丢段无重复）。
- `build_videoprobe.bat` → 诊断任意视频目录的卡片聚合与逐文件可解析性。
- `build_flickerprobe.bat` → 黑条诊断：逐帧暗像素占比 + 横/竖黑带 + 重复帧统计（`tests/flicker_probe.cpp`）。

### 第十一轮：整屏捕获 + 黑条根治 + 录屏页改版
用户反馈：录制窗口问题多（改整屏）、每笔暂停时缓存视频出现黑色条状闪烁、
纯移动不应计入录屏时间，并要求录屏页改版（滑块开关、可改缓存/导出路径、

  GPU 表面就被下一帧覆写 → 撕裂/黑边。暂停→恢复写入的瞬间缓冲轮转最快，故表现为

  改为「绘画文档名变化」——整屏下前台窗口频繁切换（点我们自己的界面、任务栏），
  按句柄判断会把录制切碎。
- **纯移动不计入录屏时间**：鼠标移动仅在「按住左键运笔」时刷新活跃时刻；
  数位笔仅在「笔尖接触」时刷新。悬停/划过不再延长录制，而长运笔不被切断的
  既有修复保留（接触/拖动中的采样仍持续刷新）。
- **录屏页改版**：新增「录屏设置」卡 —— 是否录屏（点击滑块，切换后即时启停）、
  视频缓存路径与默认导出路径两行「更改…」；移除标题栏与设置页的「打开录屏目录」按钮；
  点卡片任意处（含导出按钮）= 导出该文档全部录制，「清空」仍优先判定且需二次确认。
- **可配置路径**：`Config` 新增 `videoCacheDir` / `exportDir`（空 = 系统默认）。

- 附带修正一个既有缺陷：习惯概览状态标签用 `L"%s"` 传 `const char*` 是未定义行为

### 第十二轮：多品牌数位设备兼容加固
起因是评估「对所有品牌数位屏/数位板的兼容性」。结论：**架构方向本来就是对的**
（纯描述符驱动、无品牌白名单、压感量程自适应），但存在若干会造成**静默错误数据**
的结构性缺陷。因开发者只有 Wacom、无法测其他品牌，本轮的核心是建立
「不看设备也敢发」的离线验证能力，再逐项修缺陷。

**先澄清两个常见误解**（避免后续走弯路）：
- 本项目**没有硬编码字节偏移**。解析全程用 `HidP_GetValueCaps`/`HidP_GetUsageValue`
  按 Usage 取值，Report ID 前缀、跨字节位域、非 8 位对齐都由 HidP 处理。
  「Wacom 10 字节 / Huion 8 字节」的差异对解析透明。另：`HIDP_VALUE_CAPS`
  **只有 `BitSize` 没有 `BitOffset`**，「自己按位切分报文」技术上不可行。
- **不走 OpenTabletDriver 路线**。OTD 是 user-mode driver，要用 WinUSB/libusb
  取代厂商驱动、独占设备（官方 FAQ 要求卸载系统里所有其他数位板驱动），
  绕过 HIDClass 后才拿不到 preparsed data、只能自己解析裸字节，
  所以要维护 300+ 份 JSON 配置与专用 parser 类（其 `Report Parser` 字段存的是
  **C# 类全限定名**，解析逻辑编译进二进制）。且 OTD 在 Windows 上
  **默认拿不到压感**（官方 FAQ：no built-in support for pressure，需另装
  VMulti Driver + WindowsInk 插件）。我们站在 HIDClass 之上，这份代价不必付。
  值得借鉴的只有它的 **Attributes 覆写机制**（见下）。

**建立离线测试能力（本轮地基）**：
- `PHIDP_PREPARSED_DATA` **无法离线构造**（SDK 无任何接受原始描述符字节数组的函数），
  所以「造 Huion 描述符喂给解析器」这条路走不通。改为把唯一直接接触 `HidP_*` 的
  取值步骤抽成可注入接缝（`PenInput::HidFetchFn` + `SetHidFetchForTest`），
  测试注入 mock 直填 X/Y/压感/Usage，即可在无硬件下驱动解析→映射→归一全链路。
- `Dev` 从 private 嵌套类型提取到 `PenInputDev.h`，测试可直接构造任意能力组合。
- `build_peninput_test.bat` + `tests/test_peninput.cpp`：**127 项断言**，覆盖
  压感量程 8191/4095/1024/512/256/255、**非零 pressMin 下限扣除**、逻辑范围归一
  与非归一、相对模式累加与边界夹取、报文形态 0/1a/1b 与缓存复用、6~19 字节报文、
  按钮开关语义、纯触控屏、无压感设备、复合设备多 Report ID、**LinkCollection
  精确取值与回退**、**候选消歧纯函数**、**覆写解析与非法配置拒绝**。

**修复的缺陷**：
- **`RIDEV_PAGEONLY` 注册整个 0x0D 页**（原为硬编码 `01/02/04/0C` 四个 usage，
  且 `U_DIG_TOUCH_PAD 0x05` 定义了却从未放进数组）。依据本机实测：Wacom 笔数据
  **935 条报文 100% 落在 usage 0x01**，而 0x02/0x04/0x0C **均为 0 条** ——
  笔落在哪个顶级集合完全由厂商驱动决定，不可预测（连 OTD 都要人工指定 `WinUsage`）。
  漏注册的后果是「完全无数据且日志不报任何错」。注册失败时自动回退旧清单。
- **LinkCollection 精确取值**（本轮最重要的正确性修复之一）：
  `HidP_GetUsageValue` 第三参数原**硬传 0**，而官方注释明确「同一报文里 Usage
  相同的两个字段要靠 LinkCollection 区分」，且传 0 时「只能命中第一个字段」。
  复合设备（笔集合与触摸集合都有 X/Y）上会取到**触摸集合的坐标**。
  现从 TipPressure/TipSwitch 所在 cap 反推笔集合索引，**取不到时回退 0**
  （等价改动前行为，对单集合设备零影响）。真机日志：`parse form=0 direct (link=1 penLink=1)`。
- **坐标映射根因修复**（原为纯几何猜测，本机 5 设备**全部**匹配失败）：
  探针 `tests/prop_probe.cpp` 实测证明 `GetPointerDeviceRects` 的
  `device` 是**屏幕像素**、`display` 是**物理尺寸（0.01mm）**，两者都不是逻辑单位。
  旧代码拿 HID 逻辑范围 32767 去比像素宽 7680，误差和恰为 **1.6997** ——
  与日志里本机全部设备的 score 完全吻合，即官方映射**从未成功过**。
  更严重的是旧映射公式误把 `display`（毫米）当屏幕坐标，算出的 `sx` 是
  「毫米/像素」的无意义比值；因匹配永远失败，这个 bug 一直被掩盖，
  **一旦匹配生效就会产出垃圾坐标**，故两处必须同批修。
  改用 `GetPointerDeviceProperties` 的逻辑量程（与 HID 同源可比）匹配。
  真机结果：**5/5 设备全部 `mapSrc=1` 精确匹配**（改动前全是 `mapSrc=2` 兜底），
  且 Cintiq Pro 27 的设备类型从「外接数位板」**纠正为「数位屏」**。
- **附带发现的历史缺陷**：本机显示器为 `DISPLAY1 primary X=0 W=3840` +
  `DISPLAY5 X=-3840 W=3072`，虚拟桌面宽 7680。故旧的「虚拟桌面兜底映射」
  对这台数位屏**不是无害近似而是系统性错误**——把笔坐标铺展到含副屏的 7680 宽范围，
  在数位屏右下角运笔时坐标会落到副屏区域。此缺陷因「官方映射从未成功」而被完整掩盖。
- **多候选歧义不猜**：同一台 Cintiq Pro 27 暴露两个 PEN 指针条目
  （一个 `monitor` 绑定主屏、一个 `monitor=NULL` 跨虚拟桌面，矩形不同）。
  抽成纯函数 `PickPointerCandidate`：优先选绑定显示器者；矩形一致视为无害歧义；
  确实无法区分则拒绝猜测（`mapSrc=4`），交给标定或覆写。
- **多设备笔画分桶**：原为单一 `pStroke`，所有设备采样汇进一条逻辑笔，
  数位屏 + 数位板同时用时采样会交织进同一笔画（轨迹跳变、压感错乱，落盘后无法修复）。
  改为 `map<devSeq, ActivePen>` 按设备分桶，看门狗逐桶独立判断
  （一块板静默不再误收另一块板的笔画）。`Dev::devSeq` 为进程内自增序号
  （不用 HANDLE，其值会被系统复用）。落盘新增 `"did"` 字段，**缺失时默认 0**，
  旧日志仍可读（已用真机历史日志验证）。
- **触摸数据直接丢弃**（按用户要求，不做任何计数）：`ExtractSample` 在更新
  速度追踪与全局活跃标志**之前**早退（`touch && !tip` → 返回 false），
  故纯手指触摸不进统计、不污染笔速度、不让录屏误判为在作画。
  `tipDown` 从 `tip || touch` 改为只 `tip`。对现有 Wacom 笔**零影响**
  （笔用 TipSwitch 0x42，触摸屏才用 Touch 0x33，本机是不同 handle）。
  **额外发现并修复**：Ink 回退路径有同样漏洞——`MOUSEEVENTF_FROMTOUCH`
  签名**同时覆盖手指与笔**，而 `QueryPenPressure` 对手指必然失败却退回压感 1.0
  当作笔，于是手指操作被记成画笔笔画。新增 `IsTouchPointer`
  （仅在确证 `PT_TOUCH` 时返回 true，查不到时保持原行为以免误伤笔）。
- **穷举 Report ID 加范围校验**：形态 1b 原采纳判据只有 `gx && gy`，
  而 HidP 按偏移读字节**不校验数值合理性**，错误前缀可能读出「看似合法」的 X/Y
  并被永久缓存，日志却形似成功。现要求逻辑值落在声明量程内，越界判为错位数据
  继续试下一个 ID。**刻意只加在穷举路径**：形态 0/1a 的 Report ID 来自设备自声明
  能力表，可信；对它们强校验会让描述符有小瑕疵的未知品牌从「坐标略偏」
  退化成「完全丢数据」。
- **Ink 回退补橡皮与设备类型**：`QueryPenPressure` 早已从 `PEN_FLAG_ERASER`
  取到 `eraser`，却在 `InjPenUp` 汇总时被丢弃，且设备类型硬编码 `PEN_EXTERNAL`。
  后果：任何开启 Windows Ink 的品牌（多数默认开）用笔尾橡皮擦时全部被记成
  「画笔笔画」，`Analyzer` 的「橡皮」标签恒不出现；数位屏被错记成「外接数位板」。
  新增 `PenInput::DominantPenType()`（只认有压感的笔设备，类型冲突返回 UNKNOWN 不猜）。
- **启动竞态**：本机实测三条通道**并发**（同次运笔 Raw Input 935 / WM_POINTER 941 /
  注入鼠标 243 同时到达）。若注入鼠标先于首条 HID 采样到达，会先开一条 injPen 笔画，
  随后 `RealPenSilent()` 翻转使 `InjPenMove` 不再被调用，该笔画挂在原地
  直到 400ms 看门狗挤出 → 同次运笔多记一条重复笔画。改为翻转瞬间直接丢弃不落盘。
- **标定按设备定向**：`AddCalibrationSample` 原按 `type` 广播，两块同为
  `PEN_EXTERNAL` 的板子会互相污染映射系数。改为按 `devSeq` 精确命中。
- **覆写机制（借鉴 OTD Attributes，唯一的人工逃生舱口）**：
  `%LOCALAPPDATA%\PaintingBuddy\pen_overrides.json`，按 `vid/pid/usage/pathContains`
  匹配（AND 关系，未指定即通配，但**至少要有一个**否则拒绝——防止一条规则命中所有设备），
  可覆写逻辑量程、压感上限、`penLink`、设备类型、目标显示器。
  `usage` 这一维很关键：同一块板暴露多个集合，指定它才能只覆写笔集合而不误伤触摸。
  显示器**优先用名称**（如 `\\.\DISPLAY1`）而非索引——`EnumDisplayMonitors`
  的枚举顺序不保证跨重启稳定，只填索引会让配好的文件某天突然映射到错误的屏幕。
  安全设计：单条非法**只跳过该条**，其余照常生效，绝不整份失效；
  非法量程（`Max<=Min`）、`pressureMax<=0`、量程四值不全等一律拒绝，
  避免把设备搞到不可用；每条生效都记日志，用户知道当前不是自动路径。
  解析/校验/匹配全是纯函数（不碰 I/O），故**无需真机与真实配置文件**即可离线测试。
- **实机抓到的 BOM 缺陷（离线测试盲区）**：覆写文件解析失败，
  根因是 PowerShell `Set-Content -Encoding UTF8` 与记事本都会在文件头写 BOM
  (`EF BB BF`)，`JParse` 在读到 `{` 之前就失败。离线测试直接传字符串字面量
  （无 BOM）因此覆盖不到。修在 `JParse` 入口剥 BOM ——`config.json`
  同样会被记事本编辑、同样受益；对合法 JSON 绝对安全（其首字符不可能是 BOM）。
  **失败时的安全降级已生效**：5 个设备仍全部 `mapSrc=1`，程序未崩。
- **性能与日志保护**（因放开注册而必须）：`Dev::rejected_` 让无 X/Y 能力的杂设备
  每条报文开销降到一次 map 查找；`OnRawInput` 复用成员缓冲，不再每条报文堆分配；
  hex dump 从每设备 20 条降到 5 条；`LogF` 新增 20MB 上限轮转（转 `pb.log.old`）
  ——此前无级别、无轮转、无上限。真机实测**日志 6 秒增长 0 KB**。
- **移除设备枚举的 512 上限**：原 `nDev < 512` 超限就整段跳过（界面设备列表为空，
  要等首次运笔才由懒加载补上）。改为按 256 分批读取并处理 `ERROR_INSUFFICIENT_BUFFER`。
- **修正压感注释**：`POINTER_PEN_INFO.pressure` 是系统**已归一化**的 0..1024，
  与设备原生级数无关（原注释误称「部分设备 0..4096」，会误导后续维护者
  去做按品牌适配的错误改动）。并注明原始 HID 路径量纲不同
  （本机 Wacom 0..8191，旧款 1024/512/256），必须用 `pressMin/pressMax` 自适应。

### 第十三轮：三份真实用户报告验证 + 四个缺陷修复
第十二轮建立的回传通道（设置页「导出诊断信息」）很快收到**三份真实用户报告**，
覆盖 Wacom、XP-Pen、国产屏（VID_256C）、Elan 触控板等多品牌。这是本项目
**首次拿到非 Wacom 品牌的真机数据**，一举补上了第十二轮「其他品牌未实测」的缺口。

**正面结论：多品牌适配成功。** 三份报告共同证明：
- `RIDEV_PAGEONLY` 注册生效：识别出 4~9 个设备，覆盖 `0D:01/02/04/05` 全部顶级集合
  （旧的 4-usage 清单会漏掉 `0D:05`）。
- **压感量程 1024 / 4095 / 8191 / 16383 全部正确自适应**——其中 16383 比离线测试
  覆盖的还高，证明「描述符驱动 + pressMin/pressMax 归一」对未知品牌成立。
- **坐标映射从「本机全部 mapSrc=2 兜底」变为绝大多数 mapSrc=1 精确匹配**，
  这是第十二轮映射根因修复的质的验证。
- 报告2 有真实运笔（penSamples=1133 / penStrokes=6），落笔被正确记录。

**三份报告交叉比对挖出的四个缺陷（本轮全部修复）**：
- **① 标定退化解无校验【高危】**（报告2 实证）：`AddCalibrationSample` 采纳
  最小二乘结果时只查 `ay>1e-6`，放过了 `sy≈0.0033`（正常≈0.033）的病态解，
  采纳后（mapSrc=3）笔坐标严重错位、污染数据。抽出纯函数 `EvaluateCalibration`
  加**两道闸**：拟合优度 R²≥0.98（拦噪声/非线性）+ **斜率合理性**
  （斜率×设备逻辑满量程须落在真实显示器尺寸 200~40000px 内）。后者专拦报告2
  那种「R² 很高但斜率病态偏小」的退化解——正是旧代码漏掉它的原因。
  拒绝时保留几何映射、限流记日志。
- **② 诊断报告自相矛盾【中，第十二轮引入】**（三份报告均有）：「采集状态」计数是
  **当前会话**，「pb.log 摘录」是**跨会话历史**，导致提示「从未收到任何数位设备
  报文」紧跟着上一会话的 OK 行。抽出纯函数 `ScanPenLog` 扫描日志区分会话，
  提示改为「当前会话尚无笔报文，但历史记录显示曾成功解析过」；日志摘录按
  「当前会话/历史会话」分段标注，并改为保留**最后** 400 行（旧逻辑取前 400 行，
  日志一长就把最有价值的当前会话截掉）。
- **③ 成功报文只记前 5 条【中，诊断盲点】**（报告1 XP-Pen）：前 5 条恰好全是
  悬空（tip=0），额度用尽后**落笔数据再也不记**，无法看出该设备落笔时压感/坐标
  是否正常。抽出纯函数 `DecideReportLog` 改为「前 3 条基线 + 关键跳变
  （落笔/首次压感/橡皮/抬笔）各记一次」，跳变比连续采样更有诊断价值。
  baseline 也标记已观测信号，避免「采集时笔已按下」被误报成首次落笔。
- **④ 触控板被误标为触摸屏【低】**（报告2/3 Elan 04F3、VID_256C 的 `0D:05`）：
  落入类型判定的 else 分支、hasPressure=false 被标成「触摸屏」，还参与笔映射
  （mapSrc=2 兜底）。抽出纯函数 `ClassifyDeviceType` 单独识别 `0D:05` → 新增
  `PEN_TOUCH_PAD` 类型（名称「触控板」），在 `OnRawInput` 早退（不计入笔报文、
  不触发误报提示）、`BuildMapping` 跳过（不建笔映射、不参与标定）。手指移动本就
  由触控板驱动合成鼠标事件走鼠标通道，其 HID 报文对本工具无独立价值。

**一个待证实的疑似问题（靠 ③ 的增强诊断在下一批报告中验证）**：
报告1 会话A 只有悬空 HID 报文，而 `lastRealPenSampleUs_` 被无条件设置
（`Capture.cpp:1001`）→ 关闭了 Ink 注入鼠标回退。若 XP-Pen 落笔走 Ink，

但报告1 会话B 无落笔数据、**无法证实**，需 ③ 增强的落笔跳变日志在后续报告中确认。

### 第十四轮：两份新报告定位「笔被记成鼠标笔画」+ 投递层诊断

第十三轮交付后收到两份新报告（`diagnostics_20261018_144042` / `_144046`），
用户反馈「新版本依然没有笔画」。经排查**这不是回归**，而是一个此前未覆盖的
环境形态 —— 这两类用户的笔通道从未通过。

**证据链**（两份报告一致）：`penRawReports=0`、日志无 `first WM_INPUT arrived`、
无任何 `[pen] DROP:` 行。DROP 打在 `++rawReports_` **之前**且带 `[pen]` 前缀会被
导出收录，其缺失 + 计数在 `OnRawInput` 最前部自增 ⇒ **`OnRawInput` 一次都没被调用**，
故障在投递层而非解析层。同时 `mouseStrokes=73/123`、`penStrokes=0`，而 `undo=7`、
`redo=30` 证明用户确实在作画 ⇒ **笔被记成了鼠标笔画**。

**缺陷⑤ 根因（已修）**：`IsInjectedByPen` 只认 FROMTOUCH 签名 `0xFF515700`；
其兜底分支依赖 `lastPenSampleUs != 0`，而这些用户原始报文为 0 ⇒ 该值恒为 0 ⇒
**兜底永久失效**。于是只剩签名一个判据，签名不符则整条 Ink 回退通道失效。

修复：新建 `PenInject.h/.cpp`，判定逻辑全部写成**纯函数**（`IsPenInjectedEvent` /
`IsTouchEvent`），唯一碰 Win32 的是 `CaptureInjectEvidence`。三判据按可靠性排序：
FROMTOUCH 签名（原路径优先）→ `GetCurrentInputMessageSource` 的 `deviceType & IMDT_PEN`
（**新增，与厂商签名无关**）→ 位置吻合兜底（原路径）。`MsProc` 补传 `m->flags`
（原实现拿到 `MSLLHOOKSTRUCT` 却从未读该字段）。

> 两处被 SDK 事实纠正的假设：① `IMO_INJECTED_FROM_INK` 在本项目 SDK(10.0.26100)
> **不存在**（`INPUT_MESSAGE_ORIGIN_ID` 只有 UNAVAILABLE/HARDWARE/INJECTED/SYSTEM，
> `WinUser.h:15974-15979`），故改用 `deviceType` 而非 `originId` 作判据；
> ② 测试中变量名 `far` 撞上 `windef.h` 遗留宏 `#define far`，报 C2513。
>
> 性能：`MsProc` 是高频热路径（数位笔轮询可达 1000Hz），签名已命中时传
> `queryIms=false` 跳过 `GetCurrentInputMessageSource` —— 本机 Wacom 走快路径
> 零额外开销，只有签名不命中（即这些用户的环境）才付一次查询。

**缺陷⑥ 投递层诊断（已加，只加证据不改行为）**：`Register` 成功后调
`GetRegisteredRawInputDevices` **回读系统实际生效的注册表**，逐项记
`usagePage/usage/flags/hwndTarget`，并记采集窗口句柄、所属线程与 `IsWindow` 有效性。
真机输出：`registered-table[0]: usagePage=0x0D usage=0x00 flags=0x00000120 hwnd=...2821622`
（`0x120 = RIDEV_PAGEONLY|RIDEV_INPUTSINK`，与注册意图一致）、
`capture hwnd=...2821622 thread=50460 valid=1`。
另在「原始笔静默 + `LLMHF_INJECTED` + 三判据都不认是笔」时限流记一次完整证据
（`extraInfo/flags/srcOk/deviceType/originId/pos`）并附可行动提示。

> 这三项共同回答「注册是否生效」：下一批报告若 `registered-table` 的 flags/hwnd
> 与此处不一致 ⇒ 注册层问题；若一致但仍无 `first WM_INPUT arrived` ⇒ 注册生效而
> 系统不投递，属 Ink/厂商驱动接管。**投递层根因仍未查明，不猜测、不盲修。**

**验证**：`build_peninput_test.bat` **180/180**（新增 section P 共 14 项，含
「无签名但 `IMDT_PEN` 识别为笔」这一核心修复、注入的普通鼠标/硬件鼠标不误判、
`srcOk=0` 时不采信 `deviceType` 脏数据、触摸判定四态）；`build_test.bat` 79/79；
`build.bat` 链接通过；真机设备识别 5 个无回归（触摸屏 type=4 / 数位屏 type=2 /
压感 8191+1024 / mapSrc=1 / 跨屏映射一致），CPU 0.39s、内存 46MB。

> **诚实标注的遗留局限**：`QueryPenPressure`（`Capture.cpp:691`）仍依赖 FROMTOUCH
> 签名从 `dwExtraInfo` 低字节提取 `pointerId`。无签名环境下 `pointerId` 拿不到 ⇒
> 压感退回 1.0、橡皮标志丢失。即：**笔画计数（用户可见的核心故障）已修复，但这些
> 用户的压感曲线仍是平的**。修它需 `GetPointerIds` 枚举活跃指针，存在误配风险且
> 无法在开发者机器验证，故留待下一批回传（新增日志会给出完整证据）后再决定。

### 第十五轮：CSP + Wintab 独占笔通道 —— 最后一层回退（用户授权）

第十四轮交付后收到两份新报告（`diagnostics_20261018_155346` / `_155341`），
仍然零笔画。**用户随后亲自复现了成因：CSP 开启 Wintab 后，画笔数被记成鼠标。**
这一句把第十四轮的推测彻底替换成了确定结论，也暴露出两份报告是**两个不同缺陷**。

**报告 155346（旧版生成，缺 `registered-table` 行）—— 缺陷⑦**：
`penSamples=759` 但日志里**每一条都是 `tip=0 inRange=1`**（纯悬停），
`penStrokes=0`，而 `mouseStrokes=182`、`undo=11` 证明用户确实在作画。
即：Wintab 独占时驱动只让**悬停**报文进 Raw Input，笔尖接触数据交给 CSP 消费。
而 `RealPenSilent()` 以 `lastRealPenSampleUs_ == 0` 判静默 ⇒ **悬停采样即把它置非 0**
⇒ 注入回退与「未识别注入」WARN 诊断**双双永久关闭**。这是第十四轮没修到的真缺陷。

**报告 155341（新版）—— 投递层诊断给出了答案**：
`penRawReports=0`，而注册回读 `registered-table[0]: flags=0x00000120`
（=`PAGEONLY|INPUTSINK`）、`hwnd` 与 `capture hwnd` **完全一致**、`valid=1`
⇒ **注册无误，系统就是不投递**。且无 WARN 行 —— 因为驱动是**内核态注入**，
`MSLLHOOKSTRUCT.flags` 不含 `LLMHF_INJECTED`，第十四轮的告警条件命不中。
上一轮补的诊断正是为此而加，它如期回答了「注册是否生效」这个问题。

**修复①（缺陷⑦）**：新增 `everPenTipDown_`，只在 `s.tipDown` 时置位，作为
「原始通道确实拿到过落笔数据」的判据。**没有改动 `RealPenSilent()` 本身** ——
本机三条通道并发时的重复计数守卫（`OnPenSample` 里丢弃进行中的注入笔画）依赖它
在**第一条**采样到达时翻转，而悬停报文通常先于落笔；改成落笔口径会把这道守卫
推迟到落笔之后，反而给已验证正常的路径开出重复计数的窗口。故用正交判据实现，
不动既有语义。

**修复②（最后一层回退，用户明确授权）**：`PenInject` 新增纯函数
`ShouldUseMouseFallback`，三条否决全部通过才启用：
① `hasPenDevice`（确有压感笔设备）② `!everPenTipDown`（从未拿到落笔数据）
③ `!everInjectedPen`（注入路径也没认出笔）。命中后把鼠标左键笔画按笔笔画落盘
（`type='p'`、计入 `penStrokes`），轨迹点由鼠标移动实时接管。

> 三个设计取舍值得记录，都是被报告事实纠正的：
> ① **不能用 `DominantPenType()` 当门控** —— 报告 155346 同时接了数位屏与数位板，
>    它按设计在类型冲突时返回 `PEN_UNKNOWN`（要回答「记成哪种设备」，不能猜），
>    会把回退误关。故新增 `HasPressurePenDevice()`，只回答「有没有笔」。
> ② **正向证据不能当硬门槛** —— 原打算要求「笔近期 in-range 或事件带注入标志」，
>    但报告 155341 里 `penRawReports=0` 且内核注入不带 `LLMHF_INJECTED`，两条同时
>    不成立；若据此否决，该用户仍拿不到笔画，回退等于没生效。降为**仅日志留证**。
>    误判风险改由两层兜住：单独计数 `mouseAsPenStrokes`（可审计）+ 配置项可关闭。
> ③ **补了一处竞态**：回退笔画进行中若来了真实落笔数据，立即丢弃回退笔画并交回
>    原始路径，否则同一次运笔记两条。既有守卫在这里不生效（悬停已使
>    `lastRealPenSampleUs_` 非零），必须单独按 `tipDown` 判定。

**诊断增强**：报告新增 `mouseAsPenStrokes=` 行；补上「有采样、零落笔」这一支的
可行动提示（此前 `penSamples>0 && penStrokes==0` 不触发任何分支，用户只看到
「画了却没记录」而日志一片正常）；回退启用时限流记一条含 `extraInfo/flags/
srcOk/deviceType/originId` 的完整证据。配置项 `mouseAsPenFallback`（默认 true）
可关闭，`Config.h/.cpp` 已接读取与持久化。

**回退的触发频次与生命周期**（用户追问「会有再次触发回退的机制吗」后核实并加固）：

- **判定不是闩锁**：`MouseFallbackActive()` 在每次左键按下时重新求值三条否决，
  持续生效。`mouseFallbackLogged_` 只让**日志**记一次，回退本身照常工作；
  总量看 `mouseAsPenStrokes` 计数，不看日志条数。
- **会话内单向关闭**：`everPenTipDown_`（拿到一次真实落笔）或 `everInjectedPen_`
  （注入路径认出笔）一旦置位，本会话内回退不再启用 —— 那两条路语义更准、能拿压感。
- **跨会话必须能重新触发（用户明确要求）**：全部标志是 `Impl` 成员，`Stop()` 里
  `delete impl`、`Start()` 里 `new Impl()`，而托盘「暂停记录/恢复记录」走的正是
  Stop/Start ⇒ 暂停再恢复即门控清零，回退可再次触发，日志也会再记一次；
  `mouseAsPenStrokes` 同步归零，与报告「当前会话累计」口径一致。

  这个保证原本只是对象生命周期的**副作用**。已加固为显式不变量：新增
  `Impl::ResetSessionState()` 逐个列出必须会话级复位的字段（门控否决条件、
  全部「只记一次」日志闸、原始笔通道存活信号），并在会话启动处调用，同时记一条
  `[pen] session armed: mouseAsPenFallback=… hasPenDevice=…` 作为每会话的回退
  状态锚点 —— 用户回传报告后据此确认新会话确实重新武装，而非沿用上一会话的关闭态。
  加固理由：若将来有人为「跨会话保留诊断计数」把某个标志挪到 `Capture` 单例上，
  回退会静默退化成一次性，且**不会有任何测试失败**。

  > **诚实标注测试边界**：`ResetSessionState()` 无法离线验证 —— `Impl` 是 pimpl
  > 不透明实现、定义在 `Capture.cpp` 内部，测试构造不出它。可离线保证的是门控
  > 逻辑本身：复位后的上下文（`hasPenDevice=true`、两个 `ever*` 为 false）正是
  > Q1/Q2 的输入，二者已断言「启用回退」；Q7 断言默认上下文（设备未枚举）不误开。
  > 「复位确实被调用」这一步只能靠 `session armed` 日志在真机报告中印证。

**一个如实指出的风险窗口**：从会话启动到首次落笔之间，只要机器上有数位笔设备，
用户用真鼠标按住左键拖动（拖图层面板、用鼠标画笔）会被记成画笔。健康用户身上窗口
通常很短（碰一次笔即关闭），但每次暂停/恢复都会重新打开。这是上一轮把「笔近期
in-range」降为**仅留证**（而非硬门槛）的代价 —— 否则报告 155341 那种
`penRawReports=0` 的真需求会被否决掉。现有兜底只有两层：单独计数可审计、配置项可关。
若将来要收窄，可加「会话启动后延迟数秒才允许回退」的时间门槛，但那会偏离
「宁可来源不精确也要有笔画」的既定取向，故未擅自实施。

**验证**：`build_peninput_test.bat` **187/187**（新增 section Q 共 7 项，以两份报告
的真实状态为蓝本：155346 的「悬停不阻止回退」、155341 的「完全静默且无注入标志
仍启用回退」，以及三条否决、健康环境不误开、默认上下文安全）；`build_test.bat`
**91/91**（改动含 `Config.cpp`，故必须回归）；`build.bat` 与 `build_beta.bat`
均构建成功（测试版 `v20261018_171000`，**未运行** —— 运行会触发首启清理）；
二进制字符串校验确认新诊断文本已进两个 exe。

> **诚实标注的遗留局限**：这条回退是**有损**的 —— 没有压感、没有橡皮，只保住
> 笔画计数与轨迹形状。要拿回压感，唯一正解是用户在绘图软件里把笔输入从 Wintab
> 改回 Windows Ink（报告里已把这句写成可行动提示）。若用户不改，`GetPointerIds`
> 枚举活跃指针或许能取到压感，但存在误配风险且无法在开发者机器验证 —— 第十四轮
> 已说明为何不轻率实施，本轮结论不变。
>
> **仍需用户回传确认**：两份报告分别命中回退的两侧条件，但**没有任何一份是在
> 回退生效后产出的**。因此「CSP+Wintab 下笔画数恢复正常」目前只有纯函数层面的
> 保证（Q1/Q2 直接以这两份报告的状态为输入），尚无真机报告印证。
